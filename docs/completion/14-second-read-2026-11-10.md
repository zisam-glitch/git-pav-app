# Second read of the backend routes, 10 Nov 2026

Plan item 20 of the readiness plan ([`13-readiness-plan-2026-11-10.md`](13-readiness-plan-2026-11-10.md)): the
second read of `van.ts`, `admin.ts`, `auth.ts` and the payments webhook that was owed from the 9 Nov triage.

## What this covers, and what it does not

This is a **targeted read, not a full line-by-line one**. Read in full:

- the list of every route in the four files with the middleware on each (all 4 files);
- `auth.ts`: `check-email`, `login`, `refresh`, `sessions`, `mfa/disable`;
- `van.ts`: the patient routes (`requests/:id`, `payment-retry`, `cancel`);
- `payments.ts`: saved-card routes (`default`, `delete`) and the webhook from signature check to the
  `payment_intent.succeeded`, `amount_capturable_updated` and start of `canceled` handling.

**Not read:** the bodies of the `admin.ts` handlers, `van.ts` operator routes (`accept`, `decline`, `phase`,
`shift/*`), `auth.ts` `register` and the email, password-reset and MFA-request routes, and the rest of the
webhook (`canceled`, disputes, refunds). Nothing was run: the backend suites need a database. A full read of the
remainder is still owed and should be done before the penetration test.

## Result

No data-loss, payment-integrity or patient-data exposure bug found in what was read.

What checked out:

- **Admin:** every one of the 27 routes has `requireAuth` and `requireRole("admin")`.
- **Van:** every operator route has `requireRole("operator")`. Patient routes load the request and compare its
  `patientId` with the caller's profile before returning or changing anything; an operator may only read a request
  on their own shift.
- **Payments:** saved-card routes look the card up by `{ id, userId }`, so one patient cannot touch another's card.
  The webhook verifies the signature, claims the event row before acting (so a retry is not answered "duplicate"),
  confirms a booking only from the matching unexpired hold, refunds a deposit that arrives too late, and releases a
  van deposit authorised after the request ended. It writes an audit entry for each.
- **Auth:** login answers a wrong password, an unknown email, an inactive account and a locked account the same way
  (and spends the same time on the password check). Staff always need a second factor. Refresh rotates the token,
  tolerates a race for 30 seconds and revokes the session on reuse after that. Turning MFA off needs the password,
  a fresh code and is rate-limited.

## Findings

| ID | Severity | What | Where | Effort |
|---|---|---|---|---|
| S1 | Medium | **No limit on guessing one account's password from many IPs.** `login` counts failures per account but never sets `lockedUntil` (the check for it can never fire from this route), and the lockout it does apply is per account **and per IP**, with the IP taken from the first `X-Forwarded-For` value the caller sends, which a caller can set to anything. The route-wide limiter uses `req.ip` and does hold for a single source, so this matters for a spread-out attack. Staff are protected by their second factor; patients are not unless they turned it on. The 15-character minimum password length helps. | `auth.ts:177-206` | S |
| S2 | Low | **Five wrong passwords make the app send the real owner a security code.** `isSuspiciousLogin` forces a step-up when the failure counter is 5 or more, and the counter is only cleared by a correct password. Anyone can trigger code messages to a patient's phone or email (the code requests are limited to 5 per 15 minutes). | `auth.ts:211-225` | XS |
| S3 | Low | **Removing a saved card fails if Stripe has already detached it.** `paymentMethods.detach` is not wrapped, so the error returns a 500 and the card stays in the patient's list. It should treat "no such payment method" as already done. | `payments.ts:290-300` | XS |
| S4 | Low (accepted) | `POST /auth/check-email` tells anyone whether an email has an account. Rate-limited, and sign-up reveals the same thing. A deliberate trade for a simpler first screen; note it for the penetration test. | `auth.ts:76-87` | – |

## Suggested next steps

1. S1: also limit by account alone (for example 10 failures in 15 minutes across all IPs, answered like a wrong
   password), and take the IP from `req.ip`, not the raw header. Needs a security decision on how strict to be.
2. S2 and S3 are small and can go in one pull request.
3. Finish the read of the parts listed under "Not read" before the penetration test.
